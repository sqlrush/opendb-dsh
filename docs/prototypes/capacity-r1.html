解读与处置优先级 模型解读 · 引用的数字均有出处 · 平台只读，处置由 DBA 执行

根因串联
这个库"大"的原因有两层：清理前 174 GB 里 82% 是压测 schema（已删）；剩下 58 GB 里又有 45% 不是业务数据——16 GB 的 statement_history 是 L2 全量 SQL 追踪（每条语句连计划带等待事件）留下的空洞，行数已经从 730 万滚到 10 万，空间却一点没还；8.25 GB 的 WAL 由 checkpoint_segments = 256 决定，是参数问题不是负载问题。增长本身不是风险（73 h 净增 0.1 GB），风险在于 gsbench 42 张表从未 analyze——这直接解释了 Top SQL 报表里 fact_sales 全表聚合的坏计划和 08-28 的超时。
处置优先级
P1
statement_history：把 track_stmt_stat_level 从 L2,L2 降到 OFF,L0（或 L0,L1 保留慢 SQL），再 VACUUM FULL 回收 16 GB；平台的 Top SQL 只依赖慢 SQL 部分 CAP_STMT_HISTORY_BLOAT
P2
对 gsbench 42 张表执行 ANALYZE（fact_sales / plan_data / order_items 优先），再看 Top SQL 报表的计划是否改变 CAP_STATS_NEVER
P3
pg_log 定一条保留策略（如 30 天）并纳入巡检；WAL 8.25 GB 若嫌大可把 checkpoint_segments 调回 64–128，与 08-27 健康报告的 checkpoint 频率一起权衡 CAP_LOG_RETENTION CAP_WAL_SIZE

口径：大小一律按二进制（pg_size_pretty 口径，1 GB = 1024³ B）。目录级 = 容器内 du（磁盘实占）；对象级 = pg_total_relation_size（逻辑大小，稀疏文件下会略大于实占，两者不互相加总）。增速 = 观测窗内样本的线性回归斜率；满盘天数 = 磁盘可用 ÷ 增速，增速 < 0.1 GB/天不外推。事件标注来自平台字典的 added / removed 批次。数据源全部只读：pg_database_size · pg_tablespace_size · pg_total_relation_size · pg_stat_user_tables · pg_ls_dir / pg_stat_file · pg_settings · pg_replication_slots · snapshot.snapshot。
