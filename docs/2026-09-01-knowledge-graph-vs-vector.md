# 知识库存储分工：图数据库存客户专属知识，向量库做语义召回

> 2026-09-01。缘起：user 让我核查一套用图数据库做知识库的同类产品（BIC-Agent / DBAIOps 2.0，Neo4j），
> 判断"图库是不是弱模型的拐杖、强模型时代还要不要"。结论是要，但只在特定场景要。
> 本文定策略并给出数据库诊断场景的划分，作为知识库设计稿之前的定论。

## 一、codex 2026-07-27 实测（改密码前登录后台逐项读取，非看 PPT）

对标产品 = **BIC-Agent / DBAIOps 2.0**，知识图谱驱动，底层 **Neo4j 属性图 + 规则关系**（无 RDF/OWL 本体推理、无 GNN、无概率图模型）。

- 图谱资产：健康模型 **175**、故障模型 **870**、运维知识 **2,348 条**；故障模型能关联指标/阈值/频率/告警级别/知识点。
- 工具链真实存在：`kg_deep_diagnose` / `wait_event_info` / `kb_graph`；Neo4j 标签如 `bic_agent_FaultModel`、关系 `TRIGGERS` / `ACCOMPANIED_BY`。
- **压力测试（关键）**：要求"仅凭图谱给出 Oracle `log file sync` 的 3 条根因路径，每节点带实体/关系类型/node ID/来源/适用版本，不许用通用知识补全"。
  结果：能调工具、能查到故障模型、能返回 node ID、能识别关系类型，**但不能稳定输出 3 条经过验证的完整路径，随后自行从知识描述里组织因果**。
  定性：当前是 **「图谱检索 + 大模型归纳」，不是「完整、可追溯、确定性的图谱推理」**。
- codex 最终判断（原文）：
  > 顶尖模型会显著削弱知识图谱作为"**通用数据库知识补丁**"的价值，但不会替代**企业私有事实、实时数据、工具和审计关系**。
  > 它能否在顶尖模型时代继续形成壁垒，取决于图谱中是否沉淀了真正**私有、可验证、版本化、能多跳查询**的知识。
- codex 给该产品的价值排序：1 采集诊断工具 · 2 故障规则与脚本积累 · 3 多库适配 · 4 大模型报告编排 · **5 Neo4j 知识图谱**——而非宣传上的"知识图谱第一"。

## 二、我们的结论（与 codex 一致，且能落到我们已有铁律上）

**图数据库不是"懂不懂知识"的分界，是"多跳大规模跑不跑得动"的分界；确定性来自数据模型和推理层，不来自存储引擎。**

BIC 上了最重的引擎（Neo4j）却停在"检索 + 归纳"，恰好证明：用不用图库不是能力分水岭，**边的质量（私有 / 强类型 / 带来源 / 版本化）和能否输出可验证路径**才是。

对我们：
- **公共 DBA 知识**（手册、通用等待事件、通用根因）——强模型自己就懂，用向量 + BM25 召回即可，**不必建图**。这就是"弱模型拐杖"，强模型时代可省。
- **客户专属知识 + 可审计关系 + 大规模结构化计算**——强模型也省不掉，这是图要承担的。
- 引擎按规模走：现阶段 **PG 边表 + 递归 CTE**（边在万~十万级、跳数固定）；边稳定 ≥3 跳变长路径、边 > 500 万、需要图算法/时序回放，才上 Apache AGE（PG 内 openCypher）或独立图库。图访问收在 `opendbGraph` seam 后，换引擎上层零改动。

## 三、策略：图 = 客户专属知识，向量 = 非结构化语义召回，互补

| | 向量数据库 | 图数据库（现阶段 = PG 边表） |
|---|---|---|
| 存什么 | 手册 / 工单 / 故障报告 / DBA 笔记 / 参数说明——**非结构化文本** | 对象拓扑 / 依赖 / 变更史 / 故障链 / 规范条款↔对象 / 处置路径——**客户专属结构化事实** |
| 回答 | "**可能是什么**"（像什么、近义召回） | "**和本行的什么有关**"（多跳、可追溯路径） |
| 建设 | 快：切块 → embed → 入库 | 慢：抽实体 → 归一 → 定关系类型 → 人审 → 入图 |
| 强模型时代 | 仍需要（私有文本召回） | 仍需要（私有事实 + 审计路径） |
| 一句话 | 语义召回 | 关系推理 |

界线（借 codex 一句）：**知识图谱负责给出"可能是什么"；实时工具负责证明"现在到底是不是"。** 向量在前者，图在两者之间，实时采集在后者。

## 四、数据库诊断场景划分（含 openGauss/GaussDB 口径）

### 用向量库（非结构化、公共知识、语义召回）

| 场景 | 为什么是向量 |
|---|---|
| "`log file sync` / `WALWriteLock` 等待高怎么办" | 公共知识，手册/案例语义召回；问法与原文不同也能命中 |
| "报错 `ERROR: could not extend file` / ORA-01555 什么意思、怎么处理" | 文档解释类，一次召回即可 |
| "有没有类似的慢 SQL 优化案例" | 工单/优化笔记语义相似召回 |
| "这段 WDR/AWR 文字说明什么问题" | 长文本理解 + 召回相关段落 |
| 参数说明、版本发布说明、DBA 个人笔记问答 | 纯文本，无结构关系 |

### 用图库（客户专属、多跳、可审计路径）

| 场景 | 图上怎么走 | 为什么向量做不了 |
|---|---|---|
| **变更影响面**："改 `core_acct` 这张表，影响哪些下游" | 表→视图→存储过程→定时作业→应用系统（传递闭包） | 是本行专属拓扑，模型没见过；且要跳数不定的闭包 |
| **故障传播链**："这台共享存储 IO 抖动，会波及哪些库和业务" | 存储→实例→数据库→关键业务（多跳扩散） | 结构化扩散，向量返回的是"相似文本"不是"受影响集合" |
| **变更-故障因果追溯**："周六这次故障，前 72h 有哪些变更碰过相关对象" | 故障→涉及对象→时间窗内变更单（时序 + 多跳） | 需要按对象 + 时间双维度回溯，属图 + 时序 |
| **规范约束定位**："这次 DDL 涉及的对象受哪些行内规范约束、谁审批" | 对象→条款→审批角色/窗口 | 客户私有规范与对象的绑定关系，且要可追溯到条款出处 |
| **历史处置复用（带路径）**："这个现象，本行历史上对同一根因怎么处置的" | 现象→根因→处置动作（每步带来源 node id） | 要可验证路径，不是"相似段落" |
| **RAC / 主备拓扑推理**："这个实例挂了 VIP 漂到哪、哪些服务受影响" | 实例→VIP→服务→业务（拓扑多跳） | 本行专属拓扑 + 结构化推理 |
| **合规冲突检测**："两条规范对同一对象要求是否冲突" | 条款↔对象上找矛盾边 | 集合/图运算，非语义相似 |

### 两者配合（端到端诊断，各司其职）

1. **openGauss 慢 SQL 突增**
   - 向量：召回"`query_dop` 强制串行大聚合"这类通用优化案例与手册段落 → "可能是什么"
   - 图：这条 SQL 命中的表 → 上游哪个批量作业在灌数 → 该作业本行有无变更窗口约束 → "和本行的什么有关"
   - 实时工具：EXPLAIN + dbe_perf 证明"现在到底是不是"

2. **GaussDB 主备延迟告警**
   - 向量：召回"备机回放慢/网络/大事务"通用根因文档
   - 图：本行这套主备的拓扑 + 上游是否刚做过大批量 DDL + 历史上同一主备对同类延迟怎么处置
   - 实时：查 `pg_stat_replication` 实测延迟来源

3. **系统表膨胀（statement_history 16GB）**
   - 向量：召回"全量 SQL 追踪空间治理"通用做法
   - 图：本行规范"全量追踪仅诊断窗口开启（强制）"条款 + 该对象受哪些保留策略约束 + 历史处置路径（降级重建、2h 恢复）
   - 实时：查当前 `track_stmt_stat_level` 与表体积证明

**共性**：向量给候选、图给本行专属的关系与可审计路径、实时工具给确定性判定。三者缺一：只有向量 = 不懂本行；只有图 = 召不回非结构化知识；只有实时 = 没有经验参照。

## 五、落地要点（承接前几轮）

- 图的边必须是**强类型 + 带来源 + confidence + valid_from/valid_to**；只有人确认（confidence=1.0）且在生效期内的边可进入确定性推理，其余仅用于召回与提示。
- 别犯 BIC 的错：上了图却停在"检索 + 归纳"。要么把可验证多跳路径 + 版本治理做实，要么诚实只做向量；**"上了图库但推不出可信路径"是最差档**。
- 现阶段图仍在 PG 边表；切换引擎的触发条件见第二节。
